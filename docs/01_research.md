# Ресёрч современных подходов к рекомендательным системам

## 1. Зачем нужен современный retrieval

Классические User-CF / Item-CF хорошо работают на взаимодействиях, но плохо масштабируются и не дают полноценного решения для cold start.

Современная промышленная RecSys обычно разделяется на этапы:

1. **candidate generation / retrieval** — быстро получить несколько десятков или сотен кандидатов;
2. **ranking** — более дорогой моделью отсортировать кандидатов;
3. **business rules / filtering** — убрать недоступные, уже просмотренные или нежелательные объекты.

Two-Tower относится прежде всего к первому этапу — retrieval.

## 2. Two-Tower / Dual Encoder

### Идея

Две независимые сети строят embeddings пользователя и item в одном пространстве:

```text
user features ──► User Tower ──► user embedding
                                      │
                                      │ dot product
                                      ▼
item features ──► Item Tower ──► item embedding
```

Релевантность задаётся скалярным произведением:

`score(user, item) = user_embedding · item_embedding`

Главное практическое свойство: embeddings items можно вычислить заранее, а онлайн считать только embedding пользователя и выполнять nearest-neighbor search.

### Сильные стороны

- быстрый retrieval;
- хорошо подходит для большого каталога;
- можно использовать side features;
- item embeddings можно кэшировать;
- архитектура естественно отделяет retrieval от ranking.

### Ограничения

- не моделирует последовательность действий так хорошо, как sequential models;
- качество зависит от sampling strategy;
- in-batch negatives могут содержать false negatives и быть смещены к популярным items;
- сама по себе архитектура не гарантирует cold start: cold start возможен только для признаков, которые доступны новому объекту/пользователю.

## 3. GNN

GNN строит user-item graph и распространяет информацию между связанными узлами через message passing.

Пример: LightGCN / PinSage-подобные подходы.

### Плюсы

- естественно использует структуру взаимодействий;
- хорошо моделирует связи между users/items;
- может быть полезен для sparse interaction data.

### Минусы

- сложнее пайплайн;
- требуется построение и обновление графа;
- inference и обучение требуют дополнительной инфраструктуры;
- масштабирование требует sampling / специальных индексов.

### Когда выбирать

Когда сама структура графа является важной частью сигнала: social graph, co-view, co-purchase и т.п.

## 4. LLM-based recommendation

LLM может использовать историю пользователя, текстовые описания items и контекст.

Пример постановки:

> Пользователь интересуется X, Y и Z. Какие items из разрешённого каталога наиболее релевантны?

### Плюсы

- сильная работа с текстом;
- можно использовать сложный контекст;
- естественная генерация объяснений;
- удобно прототипировать zero/few-shot сценарии.

### Минусы

- latency и стоимость inference;
- риск hallucination;
- модель может генерировать item, которого нет в каталоге;
- для большого каталога обычно нужен отдельный retrieval / catalog-constrained слой.

Поэтому LLM часто разумнее использовать как дополнительный компонент (например, для объяснений, query understanding или ranking), а не как единственный механизм поиска по миллионам items.

## 5. Transformer-based recommendation

BERT4Rec / SASRec моделируют последовательность взаимодействий:

```text
A → B → C → ? 
```

Self-attention позволяет учитывать недавний и более длинный контекст.

### Плюсы

- хорошо моделирует sequential behavior;
- учитывает порядок действий;
- подходит для видео, музыки и e-commerce.

### Минусы

- требуется последовательная история;
- сложнее обучение;
- online inference обычно тяжелее, чем у простого dual encoder.

## 6. Сравнение

| Подход | Основной сигнал | Сложность | Cold start | Сильная сторона |
|---|---|---:|---|---|
| Two-Tower | features + interactions | Средняя | Возможен при наличии features | быстрый retrieval |
| GNN | graph | Высокая | Ограничен | связи user-item |
| LLM | text + context | Средняя/высокая | Возможен | текст и объяснения |
| Transformer | sequences | Высокая | Слабый без history | последовательность |

## 7. Почему в проекте выбран Two-Tower

### 7.1. Соответствие задаче

Проект использует MovieLens 100k и ставит отдельный эксперимент с user cold start. Two-Tower позволяет построить embedding нового пользователя из доступных profile features.

### 7.2. Хорошее сравнение с первым проектом

Получается понятное сравнение:

`классический CF → neural retrieval`

при сохранении одного домена и одного датасета.

### 7.3. Реалистичная production-архитектура

Two-Tower естественно соответствует retrieval stage:

`offline item embeddings → ANN index → online user embedding → candidates → ranking`.

### 7.4. Важное уточнение про cold start

В текущем эксперименте **cold start относится к пользователю**, а не к новому фильму.

User tower не использует обучаемый `user_id` embedding. Поэтому тестовый пользователь, которого не было в train, всё равно может быть обработан по возрасту, полу и профессии.

Item tower использует `movie_id` embedding. Следовательно, утверждение «модель полностью решает item cold start» для текущей реализации делать нельзя.

## 8. Что не выбрано

### GNN

Сложнее для учебного проекта и требует отдельного графового пайплайна.

### LLM

Для MovieLens это избыточно: каталог структурирован, а задача retrieval хорошо формализуется через embeddings. Кроме того, генеративная модель требует дополнительного ограничения по каталогу.

### Transformer

Очень интересен для следующего этапа проекта, если целью станет моделирование последовательности просмотров/оценок.

## 9. Вывод

Для этого проекта Two-Tower — хороший выбор именно как **современный retrieval-подход**.

При этом эксперимент не должен формулироваться как «Two-Tower обязательно лучше Popularity». На cold-start датасете сильный popularity baseline вполне может победить по Precision@10.

Ценность Two-Tower здесь — в персонализации и разнообразии кандидатов, а окончательный бизнес-выбор должен делаться по совокупности offline и online метрик.
