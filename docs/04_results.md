# Результаты

## 1. Итоговая таблица

Оценка выполнена на **188 тестовых пользователях**, `K=10`.

В train использовано:

- 755 пользователей;
- 44 311 положительных взаимодействий;
- положительными считаются оценки `rating >= 4`.

В test:

- 188 пользователей, отсутствующих в train;
- 20 213 исходных взаимодействий.

| Модель | Precision@10 | Recall@10 | NDCG@10 | Coverage |
|---|---:|---:|---:|---:|
| **Two-Tower** | 0.1043 | 0.0206 | 0.1091 | **0.0702** |
| **Popularity** | **0.3702** | **0.0812** | **0.3881** | 0.0059 |

Таким образом, в данном эксперименте **Popularity превосходит Two-Tower по Precision@10, Recall@10 и NDCG@10**, тогда как Two-Tower обеспечивает существенно большее покрытие каталога.

---

## 2. Сценарий оценки: cold start пользователей

Для второго проекта используется **user-level split**: пользователи из test не участвуют в обучении модели.

Это отличается от классического случайного разбиения взаимодействий внутри каждого пользователя. Такой сценарий позволяет проверить, насколько модель способна работать с пользователем, которого не было среди пользователей train.

Это особенно важно для сравнения с классическими collaborative filtering подходами:

- **User-CF** требует похожих пользователей с историей взаимодействий;
- **Item-CF** опирается на историю взаимодействий пользователя с объектами;
- **Two-Tower** в данной реализации строит пользовательское представление на основе доступных профильных признаков.

### Признаки User Tower

В текущей реализации используются:

- возраст;
- пол;
- профессия.

`user_id` **не используется как обучаемый признак User Tower**. Это принципиально: иначе модель не смогла бы корректно строить представление нового пользователя, которого не было в train.

### Признаки Item Tower

Item Tower использует:

- `movie_id`;
- жанры фильма;
- год выпуска.

Следовательно, текущая реализация ориентирована прежде всего на **user cold start**. Полный item cold start она не решает, поскольку `movie_id` является частью представления фильма.

## 3. Интерпретация результатов

### 3.1. Popularity

Результаты:

- Precision@10 = **0.3702**
- Recall@10 = **0.0812**
- NDCG@10 = **0.3881**
- Coverage = **0.0059**

Popularity показывает лучшие accuracy-метрики в данном эксперименте.

Это означает, что на MovieLens 100K самые популярные фильмы являются очень сильным baseline даже для пользователей, которые не участвовали в обучении.

Особенно заметен результат Precision@10: в среднем популярные рекомендации значительно чаще совпадают с релевантными фильмами тестового пользователя, чем рекомендации Two-Tower.

При этом Coverage очень низкий:

```text
0.0059 = 0.59%
```

То есть модель использует очень небольшую часть всего каталога. Практически один и тот же набор наиболее популярных фильмов может показываться большому числу пользователей.

Это является классической проблемой popularity-based рекомендаций: высокая точность может сопровождаться низким разнообразием рекомендаций.

---

### 3.2. Two-Tower

Результаты:

- Precision@10 = **0.1043**
- Recall@10 = **0.0206**
- NDCG@10 = **0.1091**
- Coverage = **0.0702**

По accuracy-метрикам Two-Tower уступает Popularity:

| Метрика | Two-Tower | Popularity |
|---|---:|---:|
| Precision@10 | 0.1043 | **0.3702** |
| Recall@10 | 0.0206 | **0.0812** |
| NDCG@10 | 0.1091 | **0.3881** |

Однако Coverage Two-Tower существенно выше:

```text
Two-Tower: 7.02%
Popularity: 0.59%
```

Таким образом, Two-Tower использует более широкий диапазон каталога и формирует различные рекомендации для разных пользователей.

Coverage Two-Tower примерно в **12 раз выше**, чем у Popularity.

Это является главным преимуществом Two-Tower в данном эксперименте.

## 4. Почему Popularity оказалась лучше Two-Tower

Полученный результат не означает, что Two-Tower является неудачной моделью.

В данном эксперименте есть несколько причин, по которым простая Popularity может оказаться сильнее современной нейросетевой модели.

### 4.1. Небольшой размер датасета

MovieLens 100K содержит относительно небольшое количество взаимодействий для обучения сложной нейросетевой retrieval-модели.

Two-Tower модели особенно хорошо раскрываются при наличии больших объёмов пользовательских взаимодействий и разнообразных признаков.

На небольшом датасете популярностный baseline может быть очень конкурентоспособным.

### 4.2. Сильная популярностная структура MovieLens

В MovieLens есть фильмы, которые получают значительно больше оценок, чем остальные.

Поэтому рекомендация популярных фильмов является достаточно эффективной стратегией даже без персонализации.

### 4.3. Ограниченность признаков

User Tower использует только:

- возраст;
- пол;
- профессию.

В production-рекомендательной системе пользовательское представление обычно строится на гораздо большем количестве признаков:

- история взаимодействий;
- просмотры;
- клики;
- поисковые запросы;
- временной контекст;
- устройство;
- текущая сессия;
- интересы и предпочтения.

В учебном проекте эти данные отсутствуют, поэтому потенциал персонализации Two-Tower ограничен.

### 4.4. Two-Tower — это retrieval, а не полноценная ranking-система

Two-Tower решает задачу быстрого поиска кандидатов.

В production архитектура обычно состоит как минимум из двух этапов:

```text
Пользователь
     ↓
User Tower
     ↓
User embedding
     ↓
ANN retrieval
     ↓
кандидаты
     ↓
Ranking model
     ↓
финальные рекомендации
```

Поэтому сравнение Two-Tower непосредственно с простым топом популярных фильмов не полностью отражает production-сценарий использования модели.

---

## 5. Coverage как главное преимущество Two-Tower

Разница в Coverage особенно важна с точки зрения рекомендательной системы.

Popularity:

```text
Coverage = 0.0059 = 0.59%
```

Two-Tower:

```text
Coverage = 0.0702 = 7.02%
```

Popularity концентрируется на небольшом количестве самых популярных объектов.

Two-Tower, напротив, распределяет рекомендации по значительно большей части каталога.

Это может быть полезно для бизнеса, поскольку более широкий retrieval:

- уменьшает зависимость от нескольких популярных объектов;
- позволяет показывать пользователям менее популярный контент;
- потенциально увеличивает разнообразие рекомендаций;
- создаёт возможности для discovery новых объектов.

При этом высокий Coverage сам по себе **не означает более высокое качество рекомендаций**. Поэтому его необходимо рассматривать вместе с Precision, Recall и NDCG.

## 6. Сравнение с первым проектом

Результаты первого проекта:

| Модель | Precision@10 | Recall@10 | NDCG@10 | Coverage |
|---|---:|---:|---:|---:|
| Popularity | 0.0706 | 0.0483 | 0.0708 | 0.0117 |
| Item-CF | 0.0006 | 0.0014 | 0.0019 | 0.1389 |
| User-CF | 0.0104 | 0.0136 | 0.0142 | 0.3171 |

Результаты второго проекта:

| Модель | Precision@10 | Recall@10 | NDCG@10 | Coverage |
|---|---:|---:|---:|---:|
| Two-Tower | 0.1043 | 0.0206 | 0.1091 | 0.0702 |
| Popularity | 0.3702 | 0.0812 | 0.3881 | 0.0059 |

### Важное ограничение сравнения

Эти результаты **нельзя напрямую сравнивать как абсолютный рейтинг моделей**, поскольку эксперименты используют разные схемы разбиения данных.

В первом проекте train/test формируются внутри пользователей: у одного пользователя могут присутствовать взаимодействия и в train, и в test.

Во втором проекте используется user-level split:

```text
Train users → 755
Test users  → 188
```

То есть пользователи test не участвовали в обучении.

Поэтому второй эксперимент проверяет более сложный сценарий — способность модели работать с пользователями, отсутствующими в train.

Корректнее использовать результаты первого проекта как контекст и демонстрацию различий между подходами, а не как строгое соревнование моделей.

## 7. Основные выводы

### 1. Popularity является очень сильным baseline

На данном датасете Popularity показала:

- Precision@10 = 0.3702;
- Recall@10 = 0.0812;
- NDCG@10 = 0.3881.

По всем трём accuracy-метрикам она существенно превосходит Two-Tower.

Это показывает, что использование современной архитектуры само по себе не гарантирует превосходства над простым baseline.

---

### 2. Two-Tower обеспечивает более высокое покрытие каталога

Two-Tower:

```text
Coverage = 0.0702
```

Popularity:

```text
Coverage = 0.0059
```

Таким образом, Two-Tower использует примерно в 12 раз большую долю каталога.

Это является важным преимуществом с точки зрения разнообразия и персонализации рекомендаций.

---

### 3. Two-Tower подходит для user cold start

В текущей реализации User Tower не использует `user_id` как обучаемый признак.

Представление нового пользователя строится по его доступным профильным признакам:

```text
age + gender + occupation
          ↓
      User Tower
          ↓
    user embedding
```

Поэтому модель может сформировать embedding пользователя, который отсутствовал в train.

При этом это не означает, что решены все варианты cold start: в частности, текущий Item Tower использует `movie_id`, поэтому полноценный item cold start не реализован.

---

### 4. Наиболее практичным решением является комбинация подходов

Результаты показывают, что у двух подходов разные сильные стороны:

| Подход | Основное преимущество |
|---|---|
| Popularity | высокая точность |
| Two-Tower | персонализация и более высокий Coverage |

Поэтому для production-системы можно использовать двухэтапную стратегию:

```text
                  ┌── Popularity ───────┐
User ─────────────┤                     ├── Candidate pool
                  └── Two-Tower ────────┘
                            ↓
                     Ranking model
                            ↓
                  Финальные рекомендации
```

Popularity может использоваться как источник кандидатов и fallback, а Two-Tower — для персонализированного retrieval.

---

## 8. Ограничения текущего эксперимента

Текущая модель является учебной реализацией и имеет несколько ограничений.

### Данные

MovieLens 100K значительно меньше production-датасетов современных рекомендательных систем.

### Признаки

User Tower использует ограниченный набор пользовательских признаков.

### История пользователя

В текущей user cold-start постановке история взаимодействий пользователя не используется для построения User Tower.

Это позволяет честно исследовать cold start, но ограничивает качество персонализации.

### In-batch negatives

При обучении используются in-batch negatives. Такой подход эффективен вычислительно, но распределение отрицательных примеров зависит от состава batch.

Для улучшения можно использовать:

- hard negatives;
- popularity-aware sampling;
- дополнительные negative sampling стратегии.

### Retrieval вместо ranking

Two-Tower предназначена прежде всего для генерации кандидатов.

Для полноценной production-рекомендации нужен дополнительный ranking-этап.

---

## 9. Возможные улучшения

| Улучшение | Что позволяет получить |
|---|---|
| Hard negative sampling | Более сложные отрицательные примеры и потенциально более качественное разделение кандидатов |
| Более богатые user features | Более точная персонализация |
| История взаимодействий | Использование реальных интересов пользователя |
| Sequential models | Учёт порядка и контекста действий пользователя |
| ANN вместо полного перебора | Масштабирование retrieval на большие каталоги |
| Ranking model после retrieval | Более точное ранжирование кандидатов |
| Hybrid Two-Tower + Popularity | Комбинация персонализации и сильного popularity baseline |
| A/B-тестирование | Проверка влияния рекомендаций на реальные бизнес-метрики |

Конкретный эффект этих улучшений необходимо проверять экспериментально; заранее гарантировать определённый прирост Precision или NDCG нельзя.

## 10. Итог

Эксперимент показывает, что **Two-Tower не превосходит Popularity по offline accuracy-метрикам на MovieLens 100K**:

```text
Precision@10:  0.1043 vs 0.3702
Recall@10:     0.0206 vs 0.0812
NDCG@10:       0.1091 vs 0.3881
```

Однако Two-Tower имеет существенно большее покрытие каталога:

```text
Coverage:      0.0702 vs 0.0059
```

Таким образом, результат эксперимента подтверждает важный практический вывод:

> **Современная модель не обязательно должна побеждать простой baseline по всем offline-метрикам.**

В данном проекте Two-Tower демонстрирует другой класс преимуществ — возможность персонализированного candidate retrieval для новых пользователей по их признакам и существенно более широкий охват каталога.

Для production-системы наиболее перспективным вариантом является не безусловная замена Popularity на Two-Tower, а **гибридная архитектура**, в которой Popularity используется как сильный baseline и fallback, Two-Tower — для персонализированного retrieval, а итоговый выбор рекомендаций выполняет ranking-этап.
